# Spike 0.6: SHACL engine for ADR 0005

Date: 2026-11-14. Timebox: about 3 hours. Scratch code was kept outside the
repository. Input for the maintainer's decision on
[ADR 0005](../adr/0005-schema-and-vocabulary-registry.md); the work itself
is planned for 0.7.

## Test material

- **Shapes.** The official host (healthdataeu.pages.code.europa.eu) and
  code.europa.eu were blocked by the spike's network proxy. We used a
  third-party copy of the release 7 shapes, taken from the release 7
  validator configuration (`public-shapes.ttl` and `range.ttl`, [1]). We
  did not compare it with the official file. We found no copy of the
  release 7 `mdr-vocabularies.shape.ttl`, so for the vocabulary checks we
  used the **release 8** copy and its 23 code lists [2]. Release 8 exists;
  ADR 0005 still says release 7 is the latest.
- **Data.** We wrote the samples ourselves: one valid dataset and one
  invalid dataset with 7 known faults (wrong `accessRights`, no
  `applicableLegislation`, no `hdab`, `hasStructuredData true` without
  variables, `minTypicalAge` as a string, a publisher with two contact
  points, a contact point with neither email nor page). We also wrote a
  copy of the valid dataset as a DSP 2025-1 `Dataset` in JSON-LD, using
  the DSP context plus extra prefixes.
- **Reference.** The EU ITB SHACL validator (Apache Jena 6.1.0 with
  TopBraid SHACL 1.5.0) with the same shape files.

**Correctness.** All three engines give the same result: the valid sample
passes, the invalid sample gives exactly the 7 expected violations, and
the release 8 vocabulary shapes add 1 (a health category that is not in
the EU list). All three accept one property shape in release 7 that has
no `sh:path` (it is not valid SHACL [3]) and treat it as a node
constraint. `sh:extends`, used twice, is not in the W3C SHACL vocabulary
[4], so every engine ignores it. rudof's report replaced the shape's
`sh:message` with a generic text in 2 of the 7 results. ITB and our
prototype kept it.

## Constraint components used

Counted in release 7 `public-shapes.ttl` and `range.ttl`, plus release 8
`mdr-vocabularies.shape.ttl`: `sh:nodeKind` 89, `sh:minCount` 46,
`sh:node` 41, `sh:class` 27, `sh:hasValue` 26, `sh:maxCount` 19,
`sh:datatype` 5, `sh:or` 3, `sh:pattern` 2. Targets: only
`sh:targetClass`. Paths: a single IRI, plus `sh:alternativePath` twice.
The full release 8 validator set adds one SHACL-SPARQL constraint
(`graph-guard.ttl`: "the graph has at least one dcat:Dataset") and
`sh:targetNode`.

## Measurements

The release binaries are static musl, built with the repo's release
profile. Peak memory comes from GNU `time`; times are the program's own.
"One dataset" means release 7 public + range shapes and one sample.

| | rudof `shacl` 0.3.39 | Own subset (oxrdf, oxttl, oxjsonld) | ITB sidecar (JVM) |
|---|---|---|---|
| Crates, normal deps (not yet in Portitor's lock) | 235 (140) | 22 (11) | n/a (Java 25, 328 jars) |
| `cargo deny check` with repo `deny.toml` | **fails**: see below | passes | n/a (EUPL-1.2 [7], separate process) |
| Builds on Rust 1.89 | yes | yes | n/a |
| Binary vs hello world (425 KiB) | 4.7 MiB (+4.3 MiB) | 1.04 MiB (+0.63 MiB) | image 787 MB |
| Memory, one dataset | 4.1 MiB | 1.4 MiB | 284 MiB idle, 350 MiB after use |
| Time, one dataset | 15 ms (13 ms of it to load shapes) | 3 ms | 30 to 50 ms per HTTP call when warm, 1.3 s for the first |
| With code lists, pruned (40k triples) | 66 MiB, 0.26 s | 54 MiB, 0.69 s (not optimised) | not measured |
| With code lists, full (453k triples) | 664 MiB, 3.3 s | 581 MiB, 4.5 s | not measured |
| DSP JSON-LD, contexts only from local files | yes (we parse with oxjsonld first) | yes | n/a |

How rudof fails `cargo deny`, all through dependencies it cannot turn
off with `default-features = false`:
- licences not on our list: MPL-2.0 (`colored`, `option-ext` via `dirs`)
  and CDLA-Permissive-2.0 (`webpki-roots`);
- banned feature: base64 `simd-unsafe`, through `reqwest` and
  `hyper-util`. reqwest is a fixed dependency of `rudof_iri`, so the
  `shacl` crate itself pulls it in, not only `rudof_lib`;
- unmaintained crates: `paste` (RUSTSEC-2024-0436) and
  `proc-macro-error2` (RUSTSEC-2026-0173, through `tabled`);
- vulnerabilities: two in `quick-xml` 0.37, through `oxrdfxml` 0.2.5
  (RUSTSEC-2026-0194 and RUSTSEC-2026-0195). No fixed `oxrdfxml` exists
  yet [6].

rudof runs without RocksDB: `oxigraph` is built with default features
off. It still brings tokio "full", rustls, an HTTP client and a SPARQL
engine. The `shacl` crate has had 46 releases since 2026-04-25, which
means a lot of API churn.

**JSON-LD (point 4).** oxjsonld 0.2.7 has
`with_load_document_callback` [5]. Without a callback it refuses every
remote `@context` (error `LoadingRemoteContextFailed`), and it contains
no HTTP code at all. With a callback that maps the DSP context URL and
its `@import` (`odrl-profile.jsonld`) to files from the 2025-1 tag [8],
the DSP dataset converts to 30 triples. An unknown context fails with
our own error. rudof's built-in JSON-LD reader sets no callback, so it
cannot read DSP messages; parse them with oxjsonld first.

**Code lists.** Most of the memory goes to the code lists, whatever the
engine. They are published as RDF/XML, and the only Rust RDF/XML parser
we found has the open quick-xml advisories. The vocabulary shapes only
read `skos:inScheme` and the `rdf:type` of concepts and schemes. If the
authority's bundle carries the code lists as N-Triples, reduced to those
triples, the memory drops from 664 MiB to 66 MiB and the results stay
the same.

## Effort for the own subset

The prototype (about 330 lines, written in under an hour) covers all of
the components listed above except `sh:pattern`. A production version
needs:
- `sh:pattern`, with the `regex` crate, which Portitor already uses;
- datatype checks of the lexical form;
- `sh:severity`, `sh:deactivated`, inverse and sequence paths, and
  recursion limits;
- a SHACL validation report;
- **refusing any shape that uses a component we do not support**, so an
  unsupported shape is never silently treated as passing;
- tests: the W3C SHACL test cases for these components, and a check
  against ITB on HealthDCAT-AP samples.

Estimate: 1,500 to 2,500 lines with tests, about 1 to 2 weeks.

## Recommendation

**An own SHACL Core subset on oxrdf, oxttl and oxjsonld**, behind the
`ShapeValidator` port. It passes `cargo deny`, adds 11 crates and 0.6 MiB,
works on Rust 1.89, and gave the same results as ITB and rudof on our
samples. Use the ITB image only in tests, as the reference engine, not at
run time.

Risks, in plain words:
- **Our own SHACL bugs.** Mitigation: the W3C test cases and the
  comparison with ITB in CI.
- **Shapes that change between releases.** Release 8 already adds a
  SPARQL rule. The validator must refuse shapes it cannot check, and the
  maintainer must decide per release whether to add the component or
  leave that rule out of the bundle.
- **Code lists.** The bundle format (ADR 0005, option A) should carry the
  code lists as reduced N-Triples. The connector should not parse
  RDF/XML.
- **rudof.** It is correct and fast, but it is blocked by our policy, not
  by its quality. We should look at it again if it makes its HTTP, CLI
  and output dependencies optional (a possible upstream contribution).
  The `ShapeValidator` port keeps that swap cheap.
- **A JVM sidecar** would bring a second container of 787 MB with about
  300 MiB of memory, and an EUPL licence to note. That goes against the
  goal of a small connector.
